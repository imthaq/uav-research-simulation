# Initial Results Summary

All 9 scenarios (baseline, false_positive, false_negative, sensor_noise, latency, sensor_dropout, confidence_error, naive_fusion, trust_weighted_fusion) were run against the default 4-UAV swarm. The numbers below are averages across 5 seeded runs per scenario (seeds 42-46), taken from `results/results_summary.csv` (generated by `metrics_analysis.py --runs 5`). Per-run raw logs (also 5 runs per scenario) are saved individually under `logs/` via `run_experiments.py`, for step-by-step inspection.

**A note on a fix made after the first pass of this document:** an earlier version of `simple_swarm_sim.py` had a steering bug that made `mission_success` false in 100% of runs, including baseline with zero injected error - see "Fix applied" below. The results in this document are from the corrected simulator.

## Scenarios tested

1. baseline - no perception error, no fusion
2. false_positive - phantom detections only (rate 0.08)
3. false_negative - missed detections only (rate 0.25)
4. sensor_noise - Gaussian position noise on real detections (std 1.5)
5. latency - detections delayed 5 steps before reaching the controller
6. sensor_dropout - periodic total sensor blackouts (prob 0.02, duration 8 steps)
7. confidence_error - reported detection confidence miscalibrated (level 0.35), no fusion to compensate
8. naive_fusion - combined error profile (20% false negative, noise 1.5, confidence error 0.15), unweighted cross-UAV fusion
9. trust_weighted_fusion - same combined error profile as naive_fusion, but fusion weights each UAV's contribution by its reported confidence

## Number of runs

45 total: 5 seeded runs per scenario across 9 scenarios (`metrics_analysis.py --runs 5`, seeds 42-46). `run_experiments.py --runs 5` saves the full per-step CSV log for each individual run under `logs/`.

## Metrics collected

Every run's per-step CSV log (`logs/<scenario>_run<n>.csv`) records, per UAV per step: position, goal position, actual vs. perceived obstacle position, perception error type, confidence value, fusion mode, action taken, distance to nearest UAV, distance to obstacle, collision risk flag, unnecessary avoidance flag, missed response flag, and mission completed flag (full column list in `simulation_readme.md`).

The aggregated `results_summary.csv` (one row per scenario per run) records: scenario, run number, fusion mode, false positive rate, false negative rate, noise level, latency steps, dropout probability, confidence error level, collision risk count, unnecessary avoidance count, missed response count, fusion recovery count, mission success, average response time, total near misses, average formation error, and average confidence error.

Average confidence error (mean absolute difference between a detection's true and reported confidence) is 0.000 for every scenario except confidence_error (0.243) and the two fusion scenarios (0.121), matching each scenario's configured `confidence_error_level`.

## Fix applied: mission_success is now a real signal

**Previous state:** every scenario, including baseline with zero injected perception error, produced `mission_success: false` in all 45 runs. Root cause was in the steering logic (`_steer` in `simple_swarm_sim.py`): every other UAV was treated as a repulsion threat across the full 15-unit sensor range, the same range used for the actual obstacle. But each UAV's individual goal slot (arranged in a small circle around the shared target) sits only ~5.7 units from its nearest neighbor's slot - inside that repulsion range. Worse, a UAV that had already parked at its own goal kept repelling teammates still inbound, since it never stopped being "detected." This created a standing wall that 1-2 UAVs could never cross, in every run.

**Fix:** teammates now only trigger avoidance once genuinely close (`uav_avoidance_range`, tied to the previously-unused `safety_distance` config value), not from 15 units out. A teammate that has already reached its own goal is now treated as a known, stationary waypoint - it only pushes back within a tight safety margin (`collision_distance x 1.5`) instead of the full avoidance range.

**Result:** `uavs_reached_goal` is now 4/4 in every one of the 45 runs - nothing times out anymore. `mission_success` is now driven purely by whether an actual collision occurred during final approach, giving the metric real research signal for the first time.

## Baseline result

5 of 5 baseline runs succeeded (`mission_success: Yes`). Zero collisions, zero unnecessary avoidance, zero missed response - the swarm never encounters or reacts to a perception error, since none is injected. Average formation error is 3.682, identical across all 5 runs since there is no randomness in a zero-error scenario. Average collision-risk-flag count (near-miss-distance proximity events, not hard collisions) is 79.0 per run - this reflects UAVs legitimately flying close together during final approach into adjacent goal slots, not a safety problem, since the hard collision count is 0.

## False positive result

5 of 5 runs succeeded. Phantom detections caused an average of 62.6 unnecessary avoidance actions per run, with no missed-response impact (as expected, since a phantom is an extra detection, not a missing one) and no effect on mission success - the swarm still completes safely, just with more wasted evasive maneuvers.

## False negative result

4 of 5 runs succeeded. Missing 25% of real detections produced an average of 17.0 missed-response events per run - a UAV that never perceives an approaching threat cannot react to it - and pushed the average hard-collision count up slightly (1 collision in 1 of the 5 runs), the first scenario after baseline to actually cost a mission.

## Sensor noise result

0 of 5 runs succeeded - the single worst-performing scenario. Average hard collision count across the 5 seeds was 20.8 (24, 22, 30, 17, 11), by far the highest of any scenario, and average collision-risk-flag count (149.4) and near-miss count (84.2) were also the highest. Noisy position estimates repeatedly place the perceived obstacle in the wrong spot, so UAVs both crowd too close to the real obstacle and steer incorrectly relative to it - it never once produced a clean run in 5 seeds.

## Latency result

5 of 5 runs succeeded, with identical metrics across every seed (0 collisions, 96.0 collision-risk count, 54.0 near misses) - the swarm's speed and sensor range give it enough margin to still react in time despite the 5-step delay, and since latency is not seed-dependent in this scenario's configuration, the outcome is deterministic across runs.

## Sensor dropout result

4 of 5 runs succeeded (1 run had 3 collisions). Periodic total sensor blackouts produced an average of 10.8 missed-response events per run - a UAV in a blackout has no way to react to a real threat until the blackout ends - making it the second-most disruptive single-error scenario after sensor_noise.

## Confidence error result

5 of 5 runs succeeded. Miscalibrated confidence values alone (with no fusion to compensate) had no measurable effect on collisions, avoidance, or missed response compared to baseline - the average confidence error (0.243) closely matches the configured `confidence_error_level` (0.35) after the built-in ~0.6 base-confidence scaling, confirming the miscalibration mechanism works as intended, but on its own (without a fusion step that would actually rely on reported confidence) it has no behavioral consequence.

## Which error caused the worst behavior

Sensor noise is the clear worst case: 0/5 mission successes and an average of 20.8 hard collisions per run, both the worst of any scenario by a wide margin. Trust-weighted fusion is the second-worst by mission-success rate (0/5), discussed below. Sensor dropout and false negative are the next most disruptive by missed-response count (10.8 and 17.0 respectively), but both still succeed in 4 of 5 runs.

## Does fusion help

Fusion recovers a large share of individually-missed detections: both naive_fusion and trust_weighted_fusion ran a harsher combined error profile (20% false-negative rate plus noise plus confidence miscalibration) than any single-error scenario above, and still averaged 78.2 and 78.8 fusion-recovered detections per run, holding missed response down to 7.4 and 9.0 respectively - well below false_negative alone (17.0) at a lower false-negative rate.

However, the two fusion modes are **not equivalent on safety**, and the result is counterintuitive: naive_fusion succeeded in 4 of 5 runs (average 0.4 hard collisions: 0, 0, 2, 0, 0), while trust_weighted_fusion succeeded in **0 of 5** runs (average 3.6 hard collisions: 1, 3, 2, 8, 4) - worse than naive_fusion on every single seed. This held up consistently across all 5 seeds, so it is not sampling noise. The likely explanation is that trust-weighted fusion gives more influence to detections with higher *reported* confidence, but `confidence_error_level` in this scenario means reported confidence is itself miscalibrated (average confidence error 0.121) - so trust-weighting can end up amplifying a confidently-wrong detection rather than damping it, whereas naive_fusion's flat averaging is unaffected by confidence miscalibration entirely. This is worth investigating further rather than assuming trust-weighting is strictly safer; at these specific error levels it isn't.

## Current limitations

- Only 5 seeds per scenario. The naive vs. trust-weighted fusion comparison is directionally consistent (worse on every seed), but a larger `--runs` sample (10+) would give tighter confidence intervals on the exact collision-rate gap.
- Sensor dropout has no memory of the last known obstacle position once a blackout starts; carrying forward a decaying-confidence "last known" estimate during a blackout would likely reduce its missed-response count further.
- Sensor noise has no filtering - each noisy reading is acted on directly. A simple moving-average or Kalman-style filter on the perceived obstacle position would likely cut its collision count, which is currently the single biggest safety gap in the simulation.
- The trust-weighted fusion result needs a dedicated follow-up: is the confidence-weighting formula itself flawed under miscalibration, or is this the expected/correct behavior of trust-weighting when the trust signal is unreliable? Currently unresolved.

## What will be improved next

1. Investigate the trust-weighted fusion collision result specifically - either fix the weighting formula to discount low-reliability confidence signals, or confirm and document it as an expected failure mode of trust-based fusion under confidence miscalibration.
2. Add basic filtering (moving average or simple Kalman filter) to the sensor_noise perception path to address the largest remaining safety gap.
3. Increase seed count for the fusion-mode comparison and the sensor_noise/sensor_dropout scenarios specifically, since these are the ones with run-to-run variation in mission_success.
